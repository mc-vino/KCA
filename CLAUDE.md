# Правила проекта cashforensics

Источник истины — `ТЗ_кассовый_форензик_анализатор.md` (версия 1.0). Всё ниже —
не рекомендации, а ограничения: их нарушение считается дефектом, а не
стилистическим замечанием.

## 1. Деньги — только Decimal

Все денежные величины — `decimal.Decimal`. Никаких `float` в расчётах сумм.
Квантование до 2 знаков, `ROUND_HALF_UP`.

Внутренние сравнения — в **копейках** (`int`), где это повышает точность.
Subset-sum (§7.3) считается в копейках обязательно.

### Единственное исключение: граница ruptures

`ruptures` принимает `float`. Конвертация `Decimal → float` допустима **только**
на входе в детектор разладки (`balance.detect_level_shift_pelt`, §5.8.4).
Наружу возвращаются **индексы и даты, а не суммы**.

Это значит: функция может внутри собрать `[float(x) for x in series]`, отдать в
`Pelt`, получить точки разладки — и вернуть `ChangePointWindow` с датами. Она
не имеет права вернуть `float`-сумму или сохранить сконвертированный ряд в
модель.

Тот же принцип для `scipy` (матрица стоимостей венгерского алгоритма §5.9.2) и
для статистики: `float` живёт внутри вычисления, наружу идут решения и метки.

## 2. Детерминированность обязательна

Один и тот же вход при одной версии правил → **побитово идентичный** выход
(§13.5). Отсюда:

* **Все сортировки — с полным явным ключом.** Не `sorted(items, key=lambda x:
  x.date)`, а ключ, который однозначно упорядочивает при равных датах:
  `(date, row)`. ТЗ задаёт эти ключи явно — §5.5 («минимальное `|дата − дата_s|`,
  при равенстве — меньший `row`»), §5.7.2 («по убыванию `|diff|`, при
  равенстве — по дате, затем по индексу»), §5.11.
* **Никаких множеств и `dict` без сортировки** в местах, влияющих на результат.
  `set` внутри вычисления — можно; итерация по нему в порядок вывода — нельзя.
* **Seed из конфига.** `random`/`numpy.random` без явного seed запрещены.
  Перестановочный тест §7.3 берёт `config.seed` и записывает его в отчёт.
* **JSON** — сортированные ключи, фиксированные разделители, `Decimal` строкой.

Если сомневаешься, детерминирован ли порядок, — сделай его явным. Это дешевле,
чем ловить плавающий диф в регрессии по восьми кассам.

## 3. Запрещённые библиотеки

**pandas, scikit-learn и любые ML-библиотеки не используются.** §15 ТЗ прямо
исключает Isolation Forest, LOF и любой ML для классификации находок:
необъяснимо, малые выборки, непригодно как доказательство.

Не добавляй их «временно для прототипа». Работа с рядами — обычные `dict[date,
Decimal]` и списки; статистика — `scipy` и ручные робастные оценки (медиана,
MAD, IQR).

Закон Бенфорда — не применять при N < ~1700 (§15). На этих данных пороги и
лимиты транзакций искажают распределение первой цифры.

## 4. Context7 MCP — только для трёх библиотек

Вызывай Context7 за документацией **только** по:

* `ruptures` — PELT, модели стоимости, штрафы (§5.8.4);
* `rapidfuzz` — Jaro-Winkler и его варианты (§5.9.2);
* `syrupy` — снапшот-тесты регрессии (§11.3).

Для остальных зависимостей (scipy, numpy, openpyxl, pydantic, typer, pyyaml,
pytest, hypothesis) **не вызывай** — экономь контекст. Их API либо очевиден,
либо уже зафиксирован в каркасе.

Замечание из практики: у `ruptures.Pelt` **нет** атрибута `model` — строка
разворачивается в объект стоимости, проверять нужно `algo.cost.model`. Такие
детали стоит уточнять через Context7, а не угадывать.

## 5. Отказ вместо догадки

При недостатке доказательной базы код возвращает статус «не локализовано» **с
причиной**, а не правдоподобный результат.

Конкретно:

* Subset-sum принимается только при выполнении **всех четырёх** гейтов §7.3.
  Не прошёл — `LocalizationStatus.REFUSED_*` с заполненным
  `SubsetSumGateReport`, чтобы пользователь видел, какой именно гейт закрылся.
* Локализация ниже дневного агрегата продаж запрещена **независимо от гейтов**
  (§7.4). Ответ: «расхождение локализовано до дня и до агрегата; ниже —
  требуется Z-отчёт за `<дата>`».
* Time-fallback варианта C (§3.3) применяется только после верификации ≥ 90 %
  точно сходящихся дней. Не прошёл — остановка с
  `BLOCK_CLASSIFICATION_FAILED`.
* Нарушение V1–V3 (§5.3) — остановка, а не предупреждение.
* Счёт вне справочника не поглощается молча: отдельная строка отчёта и находка
  `UNKNOWN_ACCOUNT`.
* Любая неразобранная строка попадает в `ParseIssue` с номером и причиной.
  «Тихих» пропусков нет.

Это относится и к работе над кодом: заглушка, возвращающая правдоподобное
значение, хуже `NotImplementedError`.

## 6. Формулировки в отчётах

Инструмент **не квалифицирует** находки как хищение или мошенничество (§1.2,
§13.10). Умысел не выводится из данных.

Допустимо: «расхождение», «требует проверки», «сигнатура», «не локализовано».
Недопустимо: «фрод», «кража», «виновен», «двойная выдача» как утверждение.

Сигнатура повтора формулируется так: «повтор может быть законным (возврат
нескольких одинаковых позиций); требует точечной проверки» — и обязательно
сопровождается базовой частотой по ПКО как контекстом (§8.1).

Пользовательские строки — русский, коды находок — латиница (§12).

## 7. Ловушки, которые уже стоили неверных результатов

Они описаны в ТЗ и закреплены тестами §11.1. Не «оптимизируй» их обратно.

* **Сальдо читается из колонки 4 (E), не из 9.** Чтение из 9 дало 0 вместо
  −4 952,36 (§3.2).
* **Корр. счёт: G для дебета, E для кредита.** Перепутанные местами счета дают
  полностью ложную классификацию прихода (§3.2).
* **Якорь `^` в регулярке служебных получателей обязателен.** Версия без якоря
  отбросила выдачу клиенту «Правосуд Дмитрий», потому что строка содержит
  «суд » (§3.6).
* **Приход = только продажи + авансы.** Дебет 76.9.1 в приходе давал 579 868,96
  вместо 579 749,96 и ломал сходимость раскладки (§5.4).
* **Блоки опер-лога ищутся по заголовкам, никогда по фиксированным индексам** —
  наблюдались четыре разные раскладки (§3.3).
* **Фильтр полноты выемки обязателен**: без него копеечные инкассации дают
  бессмысленный «пол кассы» (§5.8.3).
* **Текст с ведущим `=` в Excel экранируется**, иначе `#VALUE!` (§9.1).
* **`amount` ≠ `balance_impact`.** 35 непроведённых выдач на 8 411,73 имеют
  `balance_impact = 0`: этих проводок в 1С нет вовсе. Пробел контроля — не
  причина отклонения (§4.3).
* **`LOG_IMBALANCE` вычитает ВСЕ РКО, включая служебные.** Формула §5.10
  записана как «ПКО − РКО_инкассация − РКО_возвраты», и её легко прочитать как
  «служебные не считаем». На Солигорске это давало +10 802,09 вместо эталонных
  −807,91 — ровно на сумму служебных 11 610,00. Показатель меряет физическую
  сходимость лога: судебная выплата выносит наличные из ящика так же, как
  возврат. Исключение служебных из §3.6 относится только к **сверке
  возвратов**, где им не соответствуют проводки 1С.
* **Одна проводка занимает несколько строк карточки.** В продолжениях заполнена
  только колонка «Операция» («PAX 119011650», «Розничная торговля»). На
  Солигорске таких строк 15 378 из 82 611: если считать их неразобранными,
  настоящие проблемы разбора тонут в шуме.
* **Шапка выгрузки лежит в колонке даты.** Строка «31.03.2022 - 30.06.2026»
  разбирается как дата и запускает наследование до начала таблицы. Границу
  задаёт заголовок карточки — пара «Дата/Период» + «Документ».
* **Пара «префикс + разрядность» не задаёт ряд нумерации.** На Витебске в одну
  группу из 11 цифр попали номер 1С `000000223359` и штрихкод `12258438561`.
  Перечисление пропусков между ними съело память до OOM (`SIGKILL`), а
  арифметический подсчёт дал «12 258 215 202 пропущенных документа». Число
  пропусков считается **арифметически**, ряд режется по разрывам, а плотность
  ниже 0,5 означает сквозную нумерацию организации — §8.2 велит понизить тест
  до информационного, а не показывать число.
* **Агрегация мелочи §5.11 не имеет права понижать severity.** Порог
  тривиального берётся от оборота периода: на Солигорске это 2 812,74 при
  полном отклонении сальдо 1 224,80 — под него попадает вообще всё. Наивная
  свёртка прятала двенадцать `RKO_OVERSTATED` под строкой уровня «НОРМА», хотя
  те же суммы названы поимённо в причинной раскладке. Сворачиваются только
  «НОРМА» и «ИНФО»; находки без денежной величины (`SEQUENCE_GAP`) не
  сворачиваются вовсе.
* **§5.7 и §5.9 обязаны смотреть на один и тот же ряд возвратов.** `reconcile`
  строил `daily_differences` по варианту «как есть», где служебные РКО
  считаются возвратами, а `localize` разбирал день по «скорректированному».
  Пять дней Солигорска приходили в локализацию с разницей 0,00 и оседали в
  отчёте строкой «не локализовано» — включая 13.10.2022, который попал в
  остаток только из-за судебной выплаты 11 310,00. Сверяемый ряд —
  скорректированный; «как есть» остаётся в отчёте как мера мнимого расхождения
  (§5.6), но ни свёртка, ни локализация, ни детектор лага по нему не работают.
* **Сопоставление 1:1 §5.9.2 идёт до правила единственной проводки.** Порядок
  §14 — «matching 1:1 → правило единственной проводки → subset-sum с гейтами»,
  и первый шаг не факультативен. Без него 06.12.2025 Солигорска (проводки
  2 493,51 и 80,83 против выдачи 80,83 в логе) отбрасывался как «проводок две,
  §5.9.3 неприменимо», хотя после снятия очевидной пары остаётся ровно одна
  проводка и избыток 2 075,31 — её. Это четвёртый из четырёх завышенных РКО
  эталона §11.3. Снятие пар важно и в обратную сторону: из кандидатов
  subset-sum уходят выдачи с проводкой, что сужает перебор и убирает дубликаты
  сумм, на которых закрывался гейт уникальности.
* **`findings` собирается из всех источников, а не только из сторно.** Список
  §4.3 — единая таксономия §8: локализации §5.9, сигнатуры §8, неизвестные
  счета §5.4, дисбаланс логов §5.10, срез периода §5.3. Пока туда попадали
  только находки §5.5, Витебск давал «Находок: 0» при локализованном
  расхождении 160,89. Локализации с отказом (`code is None`) находкой не
  становятся — у отказа нет кода §8, его место в разделе ограничений §16.

## 8. Порядок работы

Реализация идёт этапами §14 ТЗ: детерминированное ядро → локализация с гейтами
→ причина ненулевого сальдо → сигнатуры, отчёты, пакетный режим. Готовность
каждого этапа определена измеримым критерием, а не ощущением.

Перед коммитом: `uv run ruff check .`, `uv run ruff format --check .`,
`uv run mypy`, `uv run pytest`.

Не меняй `config/default.yaml` под конкретную кассу — конфиг версионируется
вместе с кодом, и его хеш попадает в каждый отчёт. Настройка под кассу — это
отдельный файл, передаваемый через `--config`.
